### RF-1: 変更前に検証を再現できるようにする

- PRは読み取り権限で`npm run check`を実行する。配信はmainの成功したbuildだけを対象とし、PR実行が公開用concurrencyを占有しない構成にする。Node／npm／依存の固定、通常／Pages両パスの検証、検証済みdistの配信を維持する。
- 性能計測と公開smokeの実行ソース・fixture生成・手順を`scripts/`等へ移す。既存`.cache/`や`/tmp`のファイルの存在に依存させず、出力先は引き続きGit対象外にする。既存のVite／Playwrightを活用し、計測のためだけの新依存は増やさない。
- 測定対象URL・期待するビルド・描画条件を指定できるようにする。公開smokeは配信済みファイルを照合し、公開URLの検証でローカル成果物を代用しない。TLS検証とゲーム用保存の隔離を維持する。
- 釜12台＋蒸留器12台のfixtureを生成し、合法なセーブであることを検証する。ブラウザー、寸法、演出設定、キャッシュ条件、測定方法、対象commitを結果へ記録する。
- 公開済みv2の進行中job／tripを固定fixtureとして残す。既存の固定v1 fixtureと公開済み履歴は編集しない。
- アプリを変える前に同じ手順で基準値を採取する。納品時の平均22.8ms／p95 33.2msは参考値とし、環境の違う1回の測定値を固定の合否基準にはしない。

### RF-2: 小さな不具合を回帰テストと直す

1. 素材不足の案内から未雇用イリスへ移動し、雇用・派遣後に案内も現在の状態へ変わることを確認する。案内対象のIDを保持し、文言はGameStateから導出する。
2. 知識1で最初の研究案内を開き、無効ボタンではなく対象カード等へフォーカスが移ることを確認する。無効操作の理由はそのまま読めるようにする。
3. 森画像だけを失敗させ、遺跡へ切り替えると正常な画像を読み込めることを確認する。失敗状態を画像URL単位へ整理し、代替表示も維持する。

最初に該当ケースの失敗を確認し、最小修正で成功させる。この段階で大きなコンポーネント分割やデザイン変更を混ぜない。

### RF-3: 導線を型で追えるようにする

- 移動要求は「画面」「研究ID／設備種別／冒険者ID／探索先IDなどの対象」を表す判別共用体にする。CSSセレクタ、日本語aria-label、`equipment:*`等の文字列プロトコルを呼び出し側から取り除く。表示文言は操作対象の識別子にしない。
- 対象の解決とフォーカス方針を小さな共通処理へ集約する。パネル内のDOM参照は各パネルが持ち、任意のselectorを受け取る公開APIにしない。存在しない対象・無効な対象には見出しやカードへの明確なフォールバックを設ける。
- 設備選択、探索先の仮選択、画面ごとのスクロール、モバイル詳細シートを維持する。導線だけで派遣・購入・合成等のコマンドは実行しない。
- 初回案内、素材不足、研究の前提と解放先、通常ナビを確認する。シートの開閉・フォーカス復帰、待機タブの閲覧、キーボード、320px幅と文字拡大を回帰対象にする。
- 新しいルーター、イベントバス、外部ストアの導入は予定しない。責務を分けるための小さな型・関数・hookで対応する。

### RF-4: 保存を変えず、計算と検証の境界を明確にする

- versionを指定して時間・知識・報酬を計算する純粋関数を整理し、現在のプレビュー／開始処理と履歴検証から利用する。過去の開始時研究条件として合法な候補を扱い、現在の状態から1値を再計算して古い仕事を拒否する設計にはしない。
- この段階は現行仕様と同じ許容範囲を保つ。保存schemaVersion 2、contentVersion 1、数値、仕事の残時間・確定報酬を変更せず、不整合な時間・報酬・未知versionを引き続き拒否する。
- 固定v1／v2の読込・再保存・仕事の完了、合成／派遣の開始後の研究購入、設備移動、バージョンの違う仕事の復元を検証する。素材の二重消費や保存所有権の既存テストも維持する。
- M2の隣接効果については「開始時条件を何で証明するか」「進行中に配置が変わっても何を保持するか」「追加情報が必要ならどのschemaへ移行するか」を技術判断へ残す。追加効果の計算やschema変更そのものはM2実装時に行う。検証を単に緩める変更はしない。

### RF-5: 完了判定と反映

- 各段階で対象を絞って検証し、PRの完成時と最終統合時に`npm run check`を実行する。基準は直前の177件に必要な回帰ケースを加えたものとし、件数は実行結果から記録する。
- 1440×900／1366×768／390×844／320×740、標準表示・文字拡大、キーボード、詳細シート、通常の一巡、画像失敗を確認する。旧セーブ、保存失敗、待機・引継ぎ、非表示時の非加算を維持する。
- RF-1と同じ条件で24設備の操作反応・通知集約・転送量を比較する。悪化が観測された場合に測定条件を揃えて原因を調べる。未計測の性能改善は完了条件にしない。
- PR説明へ問題、変更範囲、保持する契約、検証結果を記す。公開対象を反映した後は、配信成功と成果物の一致、公開画面の一巡・保存復元・導線・設定を確認し、未確認と成功を区別する。
- ARCHITECTURE、検証手順、PLAN、PROGRESSを実装に合わせて更新する。コードだけを整理して検証・文書を残す状態では完了にしない。

## M1の実装順

1. **データと時間の核**: 初期状態、安定したID、コマンド、tick、アイテム/レシピ定義。Vitestを導入し、費用不足・素材不足・同時消費を先に検証。
2. **補給と製造**: 雇用、派遣、帰還、共有在庫、設備配置、レシピ割当、自動生産。実UIとつなぎ、進捗と待機理由を見せる。
3. **収益と成長**: 販売、知識、研究9ノード、前提と効果の反映。最初の研究に到達する経路を検証。
4. **継続プレイ**: バージョン付き保存、残時間を含む復元、保存失敗の通知、破損時案内と初期化確認。
5. **一巡のE2Eと修正**: Chromiumで雇用・派遣・回収・生産・販売・研究・再読込を操作し、デスクトップとモバイルで確認。時間はテスト用時計で制御し、不要に実時間を待たない。
6. **文書とcommit**: 実装仕様、検証件数、未実装、次の課題を更新し、意味のまとまりでcommit。

M1の各段階も、可能な限りブラウザーで動く状態を保ちます。全モデルを作り終わるまでUIを後回しにしません。

## M1の受け入れ基準

- 新規状態から、初期素材だけでなく冒険者が帰還して持ち帰った素材を使った自動合成ができる。
- 設備を購入して合法マスに配置できる。重複・範囲外・資金不足の操作で状態と費用が変化しない。
- 同時稼働する設備が素材を二重消費せず、材料がないと待機する。
- 完成品を売って金貨が増え、研究購入で資源が減り、定義した効果が反映される。重複購入と前提未達を拒否する。
- 自動再派遣や新しい設備/レシピの解放を通じ、3要素のつながりが確認できる。
- 再読込後に在庫、金貨、研究、配置、進行中の仕事が保持される。閉じた時間は加算しない。
- 破損セーブで画面全体がクラッシュせず、復旧経路を提示する。
- 必須検証が実行され、ゲームの不変条件と一巡のE2Eが成功する。失敗・未実行があればMVP完了としない。
