# 1日1ターンの店舗営業案（設計のみ）

2026-10-26。基準はmain `2e339a3`、公開アプリはRF完了時の `c1b76ad`。ユーザーの「店のレベル・知名度・商品の需要に応じて客が来店し、並べている物から購入する」を採用要件とする。[ターン制の全体案](TURN-BASED-DESIGN-2026-10-25.md)の手動全量販売案を置き換える。RFは完了済みで、再実装しない。

**推奨は、停止した準備中に倉庫から売り棚へ品と数量を移し、『1日営業する』で150作業ポイント分の生産・探索・来店購買をまとめて計算する方式。客は棚の分だけ購入する。完成品は倉庫へ入り、翌日の準備で陳列する。** 売れ残りは棚に残り、買われていない在庫を終業時に換金しない。

以下の式・初期値・欠品行動はこのゲームへの独自提案であり、原作の内部仕様ではない。係数・閾値は実装後の一巡検証で調整できる仮値とする。アプリ実装・schema変更・追加公開はまだ行っていない。

## 3. 倉庫・棚・製作用確保

`inventory`は倉庫の数量、`shop.shelves`は棚にある数量とし、**互いに重複しない**。在庫合計は倉庫＋棚。仕掛品の材料は既に確保・控除済みで、どちらにも含めない。入出庫で在庫合計・金貨・販売統計は変わらない。仕掛品の材料を在庫へ戻したり、棚と倉庫の両方へ数えたりしない。

| 店レベル | 商品を置ける棚枠 | 1枠の数量容量 | 基礎来客数 |
| --- | --- | --- | --- |
| 1 | 1種類 | 4個 | 4人 |
| 2 | 2種類 | 6個 | 6人 |
| 3 | 3種類 | 8個 | 8人 |

同一商品は1枠だけ。解放済みの傷薬・エキス・魔力薬から選ぶ。空になった枠も品目設定は保持し、準備中に品目を外せば空き枠になる。店レベル上昇は容量を広げるだけで、品を勝手に移さない。

準備中の操作は「品目を選ぶ→数量を指定して棚へ」「数量を指定して倉庫へ戻す」。倉庫数・空き枠・棚容量を検証して、一括移動する。陳列数がその日の販売可能数の上限となり、複数客が同じ最後の1個を買うことはない。

製造は倉庫からだけ材料を取る。棚へ出したエキスは製造へ使わず、製造へ戻すには準備中に倉庫へ戻す。製作用の確保数は品目ごとに非負整数で保持し、初期案は傷薬0・エキス2・魔力薬0。棚へ移せる数量は `max(0, 倉庫数 - 確保数)` 以下。確保数は「販売に出さない下限」であり、製造による消費は許す。UIで変更でき、在庫を超える設定も将来入荷の確保として認める。原材料は常に倉庫に残る。

例：倉庫エキス3・確保2なら、陳列できるのは1個。1個を棚へ移すと倉庫2＋棚1。売れれば棚だけが0になり、倉庫2は製造へ使える。棚の最後の1個が売れても倉庫から補充しない。

新規ゲームは棚の傷薬枠を案内するが数量0、移行セーブは棚なし・数量0。最初の完成品ができた翌日に、プレイヤーが陳列する。**初版では当日完成品・探索報酬を棚へ自動補充しない。** 在庫を残す判断を明確にするため、補充予約・日中の手動割込みも保留する。

## 4. 来客・需要・購買の推奨初期値

店レベルLは店舗開始後の顧客への累計販売数Sから、`S<10: Lv1`、`10<=S<40: Lv2`、`40<=S: Lv3`とする。既存の過去の手動売上はSへ流用しない。知名度Fは0〜100、初期0。

### 来客数

`V = clamp(3, 12, 基礎来客数(L) + floor(F / 25) + T)`

Tは当日解放済みの販売商品の需要に応じた補正。高需要が1種類以上なら+1、全種類が低需要なら−1、それ以外は0。陳列や在庫の有無で需要を再抽選しない。未陳列でも市場の関心で来店し、欲しい商品がなければ購入しない。

例：Lv1・知名度0・通常需要なら4人、Lv2・知名度25なら7人、Lv3・知名度100なら上限12人。最初の傷薬だけの段階は低／通常／高需要で3／4／5人。

### 商品需要と希望商品の選択

各商品の需要は日ごとに低／通常／高を20%／60%／20%で決め、準備開始時に予報として表示する。固定seed・日番号・商品IDから決定する。品目ごとの基礎重みは傷薬6・エキス3・魔力薬1、需要倍率は低1・通常2・高3。客は解放済み商品の `基礎重み×需要倍率` に従い、希望商品を1つ持つ。未解放商品は候補にしない。

全品通常なら希望比率は6:3:1。傷薬が通常、エキスが高、魔力薬が通常なら12:9:2。高需要が「必ず売れる」を意味することはない。この重みは独自の初期案で、原作の需要式ではない。

### 一人の購入処理

一客一品・1個まで。全客について希望商品と0〜99の購買抽選値を先に生成し、抽選値80未満なら購入意欲ありとする。価格・客層別の追加判定は初版に入れない。

1. 意欲なし：買わずに退店（見送り）。
2. 意欲あり・希望商品の枠なし：買わずに退店（希望品の取扱なし）。
3. 意欲あり・希望商品の棚数0：買わずに退店（希望品の欠品）。
4. 意欲あり・棚数1以上：棚から1個減らし、当日の確定売価だけ金貨を増やす。倉庫からは引かない。

代替品の購入・別商品の再抽選はしない。これにより希望品別の機会損失を実際の客データから数えられる。非購入客の理由は排他的に集計する。単に商品が売り切れたという事実から「帰った客数」を推測しない。

来店地点は `ceil(k×150/V)`（k=1〜V）。同地点では帰還・合成処理後に、客番号順で処理する。日中に完成しても倉庫へ入るため、棚の欠品を解消しない。

## 5. 店の成長と経済の見通し

営業終了後、購入客数BだけSを増やし、知名度を `min(100, F + min(3,B))` にする。新レベルと知名度は翌日から集客・容量へ反映。準備の入出庫・合成・買わなかった客では経験や知名度は増えない。

欠品・未陳列・見送りは機会損失だけとし、初版は追加の罰金・知名度低下を設けない。家賃・広告費・清掃・賃金も追加しない。空の店を何日進めても販売実績や知名度は増えず、時間放置だけでも増えない。

初期の釜1台・イリスの机上例：第1日は倉庫に傷薬1、営業棚は0で売上0。翌日の準備でその1個を陳列し森へ再派遣。第2日には合成累計3個・知識3となり、1個を客が買った場合は金貨92・倉庫傷薬2・棚0。初研究20金貨・3知識を購入すると72金貨となる。残る2個は資産として倉庫にあり、旧一括換金の資金例は撤回する。購買0なら売上0・金貨80のまま、商品を失わず翌日以降に売れる。

Lv1・通常需要・傷薬だけ・陳列2・4人の条件では、期待販売数は `E[min(2, Binomial(4,0.8))]=1.9712個`。1個陳列した場合、1日で1個以上買われる確率は99.84%。これは仮定した式からの算出で、ゲーム実装や実プレイの測定ではない。生産は基準1釜で平均1.875個/日、通常の森1人で傷薬2個/日分なので、序盤の売上は概ね生産・補給に制約される。

後半も一日最大12客なので全商品を8個ずつ陳列しても24個全量は売れない。店の成長で販売機会は増えるが、当日品の翌日陳列・需要・素材不足により完成数と販売数は一致しない。実装後は初研究・蒸留器・遺跡到達日と在庫滞留を複数seedで計測し、初期値を調整する。

新規一巡では先に20金貨でイリスを雇う案内を維持する。派遣済みなら無資金でも無料の森探索で補給できる。棚が空のまま・未派遣のまま営業する場合は準備不足を表示するが、進行不能にはしない。既に倉庫・棚・仕掛品が全て空で未雇用・無資金の旧データへ、勝手な借金・資産補填・推測返金は加えない。既存資産を保護して案内し、新たな店舗費用で資金詰まりを増やさない。

## 6. 1日の処理順と保存

1. 所有タブ・準備phase・期待日番号とrevision・棚/倉庫/確保数の整合性を検証。レベル・知名度・需要・客列・売価をその日の入力へ固定する。
2. 日初0地点で自動再派遣予定と待機設備を開始。素材は倉庫からだけ確保し、棚には触れない。
3. 1〜150地点を現行の安定ID順で進める。帰還→合成完了→残予算があれば再派遣・新規合成→その地点の客の購入。150地点は帰還・完成・購買のみ、新しい仕事は始めない。完成・帰還は倉庫へ入る。
4. 購買ごとに棚・金貨・既存のsold/earned統計と店舗販売数の候補を更新。陳列数を超えて売らず、非購入時は資産を変えない。
5. 閉店後に成長を計算し、売れ残りは棚へ保持。準備中の雇用・設備・研究支出と営業売上を混同せず、当日分の仕入れ/製造消費・売上・変化・持越しを日報へ集計する。
6. completedDaysを1増やし、状態＋同じ日の日報＋成長＋seedを一つのJSONに保存。成功後にだけ画面状態を更新して日報を開く。失敗時は金貨・棚・倉庫・仕事・日数・seedを確定前に保つ。

結果を先に確定してから、保存済みの来店・購買イベントを演出で再生する。待機・アニメ時間・速度・スキップは計算へ入力しない。日報を閉じる・再表示・再読込で再営業しない。Web Locksと期待revisionで連打・複数タブの二重精算を拒否する。

今回から需要・希望商品・購入意欲に乱数が必要になる。seedを保存し、日/客番号/用途ごとに再現できる整数の乱数列を使う。棚不足などの分岐でも同じ客に割り当てた抽選値を飛ばさず、後の客を変えない。再試行・補充の操作・再読込・演出スキップで再抽選しない。乱数アルゴリズムと固定テストベクトルは実装時にversionへ固定する。

## 7. UIと保存する最小情報

既存4画面の「在庫・販売」を「店・在庫」へ更新し、新しい第5画面は増やさない。既存の商品・設備・人物・探索先13画像、SVGアイコン、モバイルシートを使う。客にイリス等の人物画像を流用せず、汎用アイコンと希望商品アイコンで表す。新しい客の原画や店内配置パズルは不要。

- HUD：準備中の日、「1日営業する」、営業結果再表示。実時間のカウントダウンは廃止。
- 店・在庫：店Lv/次Lvまでの販売数/知名度/本日の需要と来客予報、棚枠と各容量、品目・数量の陳列/倉庫戻し、製作用確保、倉庫と棚の数量を別表示。営業前に「当日完成品は翌日陳列」と明示する。
- 工房：倉庫で使える材料数、完成先は倉庫。棚に材料候補のエキスがある場合は倉庫へ戻す導線。移動・派遣等の既存の型付き導線を維持する。
- 初回案内：合成→翌日陳列→客へ販売→研究を案内。旧「売る」ボタンを購買なしの換金として残さない。
- 日報：来客/購入客、商品別販売数・売上・棚残数、見送り/未陳列/欠品の人数、製造・帰還・知識・倉庫変化、店経験と知名度の変化。内訳を希望商品データから集計する。過去の音や通知を再生しない。

新schemaの候補情報は、日・phase・revision・直近日報に加え、棚（品目と実数）・品目別確保数・新店舗の販売数S・知名度F・seed。L/容量/基礎来客はSとversion付きルールから導出し、重複する正本を増やさない。数量・金貨・統計は安全な非負整数を検証し、上限を越える候補は丸めず日全体を未確定として扱う。日報には当日の需要・レベル・価格と、最大12人の希望商品/結果を保持すれば足りる。全期間の客履歴は保存しない。

## 8. 旧セーブ移行

推奨はschema 3、日次・店舗ルールversion 2を追加（着手時に未使用を確認）。公開済みversion 1と固定v1/v2を変更せず、既存の仕事は開始時条件で継続する。

| データ | 移行初期値・保護 |
| --- | --- |
| 金貨/知識/材料/製品/研究/雇用/配置/過去のsold・earned統計 | そのまま。過去売上を再加算しない。旧inventoryの全量は倉庫へ入る |
| 旧進行中job/trip | 正確な残量と確定報酬を保持。移行だけでは完成せず、初回確定で通常150進める。材料を再消費・推測返金しない |
| 日と結果 | completedDays=0、準備中、「移行後 第1日」、日報なし。旧tickから暦を作らない |
| 棚 | 全て空。過去の手動販売の意図から自動で陳列しない。明示的に品と数量を移してから営業する |
| 成長 | 新店舗のS=0、知名度0、Lv1。過去の手動販売数を顧客数や来客による経験へ換算しない。既存の累計統計は別途保持・表示 |
| 確保数 | 傷薬0/エキス2/魔力薬0。資産は動かさず表示し、準備中に変更可能 |
| seed | 新規は1度生成して保存。移行は元JSONの安定ハッシュから一意に初期化し、保存失敗・再読込で抽選をやり直さない |
| 設定・所有権 | 表示設定キー、音の明示有効化、同じSAVE_KEYとWeb Lock、取得後の再読込を維持 |

新しい正本を書き込む前に元JSONを `${SAVE_KEY}-before-day-turn-v3` へ一度だけ退避する。v1用バックアップは上書きしない。バックアップ失敗では移行を確定しない。陳列ゼロの初回営業は売上0でも既存資産を失わず、倉庫と陳列の案内を出す。

## 9. 受入条件と実装時の確認範囲

1. 放置・別タブ・再開では日数/生産/客/金貨が進まず、有効な確定1回で1日だけ営業する。
2. 未陳列の傷薬100個、原材料、確保用エキスは客に売られない。陳列の入出庫だけで資産・金貨・販売実績が増減しない。
3. 客列を固定し、陳列1個を欲しがる意欲ありの2客なら1客だけが購入し、後者は欠品。倉庫に在庫があっても自動補充しない。
4. 意欲なし/希望品なし/欠品では金貨と商品が変わらず、排他的な理由の人数が実際の客列と一致する。来客数＝購入客数＋非購入客数。
5. エキス3・確保2では1個まで陳列でき、棚のエキスを製造で消費しない。戻せば製造に使える。確保数変更や入出庫で日が進まない。
6. 営業中の完成品は倉庫へ入り、その日には売られず、翌日明示的に陳列すれば客の候補になる。売れ残りは棚へ残る。
7. 需要の重み、L/Fによる来客数、容量、価格研究のfloor、成長閾値10/40を境界で確認する。成長は翌日から反映し、空営業・入出庫で増えない。
8. 同じseed・日・状態で需要/希望品/購買/結果が同じ。連打・保存失敗/再試行・再読込・複数タブ・演出スキップでも売上/資産/成長は一度だけ。
9. 保存済み日報から再開しても再営業せず、棚/倉庫/仕事/金貨と日報が一致する。候補保存の失敗は前状態を維持する。
10. 固定v1/v2の初期/研究済/仕事途中/全棚未設定へ移行し、金貨・資産・旧統計・残作業が重複/消失しない。未知schemaは保護する。
11. 初期100金貨と1釜・イリスの複数seed一巡で、初販売・初研究・蒸留器・遺跡への到達日、在庫滞留を計測する。上記の2日目・72金貨は購入が起きた場合の机上例で、全seedでの保証にはしない。
12. 通常/Pagesパス、PC/320px/文字拡大/キーボード、所有権・保存失敗を確認。24設備・最大12客でも計算結果を保存してから任意演出へ進める。

今回実施するのは現行数値との照合、式と少数例の机上確認、文書整合・リンク確認まで。上記は実装時の受入条件であり、店舗エンジンやUIのテストが既に成功したという意味ではない。
