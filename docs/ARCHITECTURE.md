# 技術構成と判断

## 現在の構成

- React 19 + TypeScript + Vite。本番成果物は `dist/` の静的ファイル。
- `src/main.tsx`: Reactアプリケーション起動。
- `src/ui/App.tsx` / `navigation.ts`: 常設HUD、型付きの移動要求、設定・記録の統合。対象は研究ID・設備種別・探索先等で指定し、各パネルがDOM参照とフォーカスを所有する。無効な操作対象にはカードや見出しへフォールバックする。`useGame`は1回だけ起動し、画面切替でも保持する。
- `src/ui/WorkshopPanel.tsx`: 設備選択、購入・移動モード、roving tabindexと矢印によるマス移動。PCは右側の詳細、1000px以下は詳細シートへ切り替える。
- `src/ui/Dialog.tsx` / `useCompactLayout.ts`: native dialogのフォーカス制限・Escape・復帰と、CSSに合わせた詳細表示の切替。ゲーム変更の無効化をシートの閉じる操作から分ける。
- `src/ui/useGame.ts`: 日次正本DayState、所有権、候補の保存成功後の更新。実時計は通知と保存表示だけに使用。一時イベントを表示層へ渡す。
- `src/game/events.ts` / `engine.ts`: 完成・帰還・販売・研究の構造化イベント。状態遷移と同時に確定し、保存データや日本語ログとは分離する。
- `src/ui/feedback.ts` / `useFeedback.ts` / `FeedbackLayer.tsx`: 同時完成の集約、最大2通知の表示、寿命管理と再読込・所有権変更時の消去。
- `src/ui/Artwork.tsx` / `AdventureBrief.tsx`: 分離した製品アート、稼働時だけの炉光・泡、画像失敗時の代替表示と冒険者要約。
- `src/artwork.css` / `src/assets/ui2/`: 画面構成のCSSから分離したアート・演出。画像はVite importで配信し、制作元とハッシュは素材READMEに記録。
- `src/style.css`: 青緑・真鍮の配色、PCの左ナビと2列工房、モバイルの下部ナビと詳細シート、本文16px・補足14px・44px操作領域、文字拡大時の再配置。
- `src/game/`: データ・準備コマンド・日次作業と購買のシミュレーション。
- `src/persistence/daySave.ts` / `save.ts`: 日次正本の保存と検証、旧世界データの検証、旧JSONのバックアップと復旧。
- `src/persistence/session.ts`: Web Locksによる書き込み所有権と解放。
- `src/persistence/migrate.ts` / `legacyV1.ts`: 凍結した旧schemaからの明示的な移行。
- `src/game/contentVersions.ts` / `workRules.ts`: 公開済み数値ルールの履歴と、合成・探索の確定結果を計算・検証する純粋関数。
- `src/game/config.ts`: 工房寸法と容量。
- `tests/unit/`: Vitestで経済・時間・研究・保存を検証。
- `tests/e2e/`: 本番ビルドを実Chromiumで操作し、一巡・製造・研究・破損復旧・保存失敗・非表示停止を検証。
- `scripts/setup.sh`: 書き込み可能なキャッシュを利用する `npm ci` とChromium確認。
- `scripts/benchmark.mjs` / `public-smoke.mjs`: 実エンジンから合法なfixtureを生成する性能・配信検証。条件と使い方は `scripts/README.md`。取得応答と結果はGit対象外へ出す。
- `package-lock.json`: exact指定した直接依存と推移的依存を固定。導入済みバージョンの正本。
- `.github/workflows/pages.yml`: PRで読み取り権限の検証を実行し、mainのpush/手動実行だけが検証済み `dist/` を公開する。PR別のconcurrencyを使い、配信を占有しない。Node/npmと第三者Actionのcommit SHAを固定。

通常の開発ではルートパスを使い、Pagesビルドでは `VITE_BASE_PATH=/Alcemy-Sim1/` を指定。`npm run check` は両パスでビルドとE2Eを実行し、最後にPages配信用成果物を残します。公開に必要な権限はdeployジョブだけに付け、初回のPages有効化はリポジトリ設定で行います。

Node.jsはCloudにある24.19.0を `.node-version` に記録。24.x以外は自動採用せず、ツール更新は検証を伴う別変更として行います。npmは11.xを利用します。

## ゲームの実装構成

```text
src/
  game/
    types.ts           Zod状態schemaと推論型・コマンド型
    content.ts         アイテム・レシピ・設備・研究の定義
    contentVersions.ts  変更しない公開済み数値ルールの履歴
    config.ts          工房寸法・容量の共通定義
    engine.ts          既存準備コマンド・作業・不足/価格/解放状態の算出
    dayTypes.ts        日次正本・日報のschemaとコマンド型
    dayEngine.ts       日送り・棚・日報確認の純粋処理
    shop.ts            需要・顧客・購買・成長の係数と固定乱数
  persistence/
    daySave.ts         日次正本の検証・原子的保存・移行バックアップ
    save.ts            旧世界データの厳密検証・version移行
  ui/                  工房・派遣・研究などのReact表示
  main.tsx             起動とReactの接続
tests/
  unit/                Vitestでコマンド・時間・整合性を検証
  e2e/                 Chromiumでプレイと保存復元を検証
```

MVPはReact標準の状態管理と純粋関数で構成し、外部状態管理ライブラリは使っていません。既存の準備コマンドと仕事処理は `engine.ts` を再利用し、日送りと店舗のルールは独立したモジュールへ分けています。

## T1の実装境界

- `dayTypes.ts`: schema 3の外側の正本と営業日報。worldのschema 2は旧世界データの厳密な検証境界であり、別の保存正本ではない。
- `dayEngine.ts`: 旧準備コマンドを再利用し、150作業/日の純粋処理、棚の入出庫・確保、report phaseと期待revisionを扱う。旧sellは日次コマンド境界でも拒否する。
- `shop.ts`: ルールversion 2の需要・希望品・意欲・来客数・成長係数。整数hash/mixのcounter-based乱数をseed/日/用途/客番号から生成し、条件分岐で後の客の抽選をずらさない。固定ベクトルを単体検証する。
- `engine.ts`: 既存の仕事計算と履歴を維持し、候補だけを変更する作業1単位と待機設備の着手を共用。旧advanceTicksは互換検証用で、useGameの実時計へ接続しない。
- `daySave.ts`: 固定v1/v2のdecodeを再利用して移行。移行元の安定hashをseedにし、旧仕事の残量と確定値を守る。所有権取得後に元JSONのバックアップ→新正本を保存する。
- 営業候補と日報を一括保存し、成功後だけReact/current refと通知を更新する。失敗時は旧状態・seedを保つ。日報の顧客列は保存時にseed/需要/開店棚/売価から照合し、Sの増分が購入客数と一致することを検証する。
- `InventoryPanel.tsx` / `DayReport.tsx`: 店・倉庫/棚と保存済み日報。計算完了後に結果を即時表示し、日報表示時間は内部計算へ入力しない。新営業の通知は前日分と混ぜず、再開では過去の通知を再生しない。

## 不変条件

- `DayState`が唯一の正本。worldを既存v2世界データの厳密なサブ文書として保持し、各パネルはそこから派生した読み取り値を受ける。棚は倉庫と重複しない。UIに資産の別コピーを持たない。
- `applyCommand(state, command)` は次状態・エラー・一時イベントを返し、失敗時は元状態と空イベントを返す。`advanceWithEvents(state, count)` は次状態とイベント、互換APIの`advanceTicks(state, count)`は次状態だけを返す。いずれも入力を変更せず、DOM、localStorage、現在時刻を直接参照しない。
- 副作用は外側から接続する。探索報酬は確定値。店舗の抽選は保存したseedと営業日から再現する。
- 計算順序は仕様に従い固定する。tickのまとめ方を変えても同一結果になることをテストする。
- 合成中ジョブは確保済み材料・残時間・完了品を保持。研究で既存ジョブを巻き戻さない。
- 研究効果は基本値と購入済みIDから再計算し、読込のたびに倍率を重複適用しない。

## 保存の方針

localStorageの現行正本はschemaVersion 3/contentVersion 2のDayStateです。worldは既存v2世界データのschema/履歴検証を再利用し、日次の棚・日数・revision・seed・直近日報を同じJSONへ持ちます。公開済みv1の構造は凍結し、移行後に厳密検証します。旧JSONは初回の書き込み前にバックアップします。読み込みデータは信用せず、有限・非負の数値、ID、配置、研究前提、ジョブ参照を検証します。未知versionや破損データを自動上書きせず、破損を案内して明示的な新規開始を提供します。

保存・初期化・日送りはWeb Locksの所有タブだけで実行します。所有権を取得したら最新データを読み直し、離脱時は保存後に解放します。待機中タブはstorage通知で表示を更新します。

表示・音の設定は `preferences.ts` で検証し、`usePreferences` がゲーム保存と独立したキーへ保存します。待機タブの設定変更もゲーム保存・バックアップへ触れません。保存できない場合も現在画面の選択を保持し、設定の失敗を表示します。`useFeedbackSound` は明示的な有効化とユーザー入力でAudioContextを開始し、新しい一時イベントのバッチに最大1音を鳴らします。音量0・非表示・初期読込の過去結果は鳴らしません。

素材不足からの移動は `materialSources.ts` が現行の素材・レシピ・設備・解放状態から導き、画面・フォーカス・選択だけを変更します。研究効果例は `researchPresentation.ts` が既存エンジンのプレビューを使い、実際のGameStateは変更しません。

画面の選択、配置モード、探索先、スクロール位置はUI内で保持します。自動再派遣先はゲームの準備条件として日次正本へ保存し、画面内の選択だけの探索先とは分けます。各パネルは非表示になっても保持し、進行と保存は画面切替から独立させます。

演出イベントはGameStateへ入れず、実処理の戻り値からUIへ渡します。読み込みから過去ログを再生せず、ページ非表示・初期化・所有権取得時に一時表示を消します。演出軽減時は静的な結果と状態を保持します。

合成と派遣の表示プレビューはジョブ生成と同じ関数を使います。数値を変更する場合は履歴エントリを追加してCONTENT_VERSIONを進めます。既存エントリを編集すると旧セーブの契約を壊すため禁止です。固定v1 fixtureと現行定義/履歴の一致テストを維持します。

### 仕事の計算と履歴検証

`workRules.ts`の`craftOutcome`と`expeditionOutcome`は、基準値・研究・ルールを受け取り、合成時間／知識と派遣時間／報酬を返す。新しい仕事は現在のカタログ、進行中の仕事の検証はそのcontentVersionの凍結した基準値を渡す。現在のカタログを変えても、過去の仕事は巻き戻さない。

研究は増えるため、保存した仕事が開始した時点では未購入だった研究もある。`isCapturedCraftValid`と`isCapturedExpeditionValid`は現在の研究を前提として合法な過去の結果を検証し、現在の結果への完全一致を要求しない。現行の許容時間・知識・報酬の範囲は維持し、未知versionや不整合値を拒否する。固定v2 fixtureと許容／拒否の境界テストも残す。RFではschemaVersion 2/contentVersion 1を維持した。T1で外側の正本をschema 3へ移行し、履歴version 2を追加した。version 1の値は凍結したまま。

### M2で追加効果を入れる際の判断

隣接効果など、研究以外の条件が時間・報酬へ影響する場合、開始後の配置から再計算してはならない。追加効果の仕様を定めた時点で、開始時の効果を説明できる最小の情報（効果種別・適用元・開始時の数など）と確定結果を保存し、そのversionで合法な組合せを検証する。任意の倍率だけを受け入れる方式は採らない。

追加情報が必須になる場合は公開済みv2 schemaを凍結し、次schemaへの明示移行と移行前データの保護を実装する。既存v2の仕事は旧versionの確定値で完了させ、新しい効果を遡及させない。「開始→配置／研究の変更→保存→再読込→完了」を境界テストにする。新しい効果・開始条件・schemaの実装はM2以降で行い、今回の共通化では検証を緩めない。

MVPでは端末間同期やオフライン加算は行いません。セーブは各ブラウザーに依存するため、将来必要ならJSONのインポート/エクスポートを追加します。CloudのE2Eテストは隔離されたブラウザープロファイルで動き、ユーザーのゲーム保存とは共有しません。

## 品質の段階

| 段階 | 必須検証 |
| --- | --- |
| M0 開発基盤 | strict型検査、本番ビルド、デスクトップ/モバイルChromiumで画面・操作・再読込、コンソールエラーと横溢れなし |
| M1 MVP | 上記 + ゲーム状態の単体テスト + 実ブラウザーで派遣→合成→販売→研究→再読込復元 |

Firefox/WebKit、画像回帰、全端末検証は現時点の任意・未実施項目です。公開確認は `DEPLOYMENT.md` と `PROGRESS.md` に記録します。
