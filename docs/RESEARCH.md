## 3つの要素を一つのループにする

| ユーザーの着想 | 本作で担う役割 | 初期検証の焦点 |
| --- | --- | --- |
| 冒険者派遣とアイテム合成 | 自分で全素材をクリック収集せず、補給先と生産品を決める | 派遣→回収→在庫消費の循環が成立するか |
| 工房内の設備配置と自動合成 | 生産能力に投資し、手作業を減らす | 複数設備が在庫を安全に共有し、配置に制約があるか |
| インクリメンタルな研究 | 稼いだ資源を生産性と新しい選択肢へ再投資する | 研究の効果が見え、次の短期目標が自然にできるか |

3要素を別々のミニゲームにすると規模が膨らみます。共通の在庫・通貨・時間軸に接続し、まず1画面で一巡させます。レシピの「解法」は初期版では研究による解放として扱い、素材の組み合わせを探す実験システムは後続候補にします。

## 技術選択の理由

- **ブラウザー + React + TypeScript + Vite**: Cloudでビルドと実ブラウザーテストを完結でき、経営画面・一覧・研究ツリーを標準HTMLで作りやすい。
- **ゲーム専用エンジンは初期導入しない**: 最初は2Dグリッドと管理画面が中心。物理演算や3D描画の必要性は確認されていません。
- **シングルプレイヤー・ブラウザー内保存**: 認証・外部DB・常時サーバーを省き、ゲームの手触りを先に検証できる。端末間同期は後続の別機能。
- **ChromiumによるE2E**: Cloudに既にある実ブラウザーを使い、追加のブラウザー配布先や秘密値を必要としない。
- **ゲームロジックにはVitestを追加予定**: 今回の準備画面に対する形だけのユニットテストは作らず、状態遷移の実装と同時に導入する。

## 主要リスクと対応

| リスク | 設計・検証方針 |
| --- | --- |
| 素材不足や資金枯渇で進行不能 | 初期補給、派遣の継続費なし、設備の再配置無料。無購入状態からの回復経路をテスト |
| 自動合成の二重消費 | 決まった順序で一つの状態遷移を処理し、素材を開始時に確保 |
| 時間の進め方で結果が変わる | 明示的なtickとイベント順序。同じ経過時間を刻み方を変えて検証 |
| 放置計算でブラウザーが固まる | MVPは閉じている間の進行なし。オフライン進行導入時は上限とまとめ計算を設計 |
| ツリーの大量追加で整合性が壊れる | 安定したID、前提条件の循環・参照切れ・到達不能を自動検査 |
| 配置が見た目だけになる | MVPでは占有・生産能力を成立させ、次段階で隣接効果・拡張を検証 |
| 保存破損・将来の互換性 | バージョン付き保存、読み込み検証、破損時の復旧UIを実装 |

後から見直せる仮決定として、日本語UI、2D俯瞰、買い切り等の課金なし、オンライン機能なしで開始します。これらの好みは現段階の進行を止める未回答事項にはしません。
