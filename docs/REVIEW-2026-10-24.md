# サブエージェントによるMVPレビュー

対象: `ee39d33e5368f2e21fa8c15303b50c4b0a1f448f`。実施日: 2026-10-24（Asia/Tokyo）。

ユーザーの依頼により、3名のサブエージェントが読み取り専用で調査し、主エージェントが所見を統合した。今回の変更はレビュー記録と進捗文書だけであり、以下の不具合修正・リファクタリングは実施していない。

## 結論

現在の純粋なゲーム処理・React UI・保存境界は維持できる。全面的な作り直しは不要。先にセーブ競合を修正し、数値調整前に保存互換性を整えた上で、画面と効果計算を段階的に整理する。

| 優先度 | 所見 | 分類・確度 |
| --- | --- | --- |
| P1 | 複数タブが古い進行を保存してしまう | 現行の不具合。実ブラウザーで再現済み |
| P2 | 数値調整だけで既存の途中セーブを拒否する | 変更時の互換性問題。メモリー上の数値変更で再現済み |
| P2 | Appに画面と操作責務が集中している | 拡張前の保守性改善。現時点の遅延は未確認 |
| P2 | UIとエンジンで研究効果を重複計算している | 保守性改善。現在の表示不一致は未確認 |
| P2 | 保存ライフサイクルを守る回帰テストが不足 | テスト範囲の不足をコードで確認 |
| P2 | 同種設備で全枠を埋めると製造系統を変更できない | 再現済みの既知仕様制限。収納等の機能追加で対応 |

P1は通常利用でデータを失うため先に修正する。P2の保存互換性は、現在の公開版内で突然壊れるという意味ではなく、次のコンテンツ変更の前提作業とする。

既存テストの成功は、複数タブや将来版との互換性まで保証するものではない。これらを直接保護するケースは現在ない。

## P1: 複数タブによるセーブの巻き戻り

根拠: [初期読み込み](../src/ui/useGame.ts#L12)、[無条件の保存](../src/ui/useGame.ts#L30)、[自動保存・離脱保存](../src/ui/useGame.ts#L81)。同じキーに対する書き込みの所有権管理も、他タブの変更検知もない。

再現手順（同一ブラウザーの同一コンテキスト）:

1. 初期状態からゲームのタブA/Bを開く。両方100金貨。
2. Aでイリスを雇い、80金貨・雇用済みのセーブが書かれたことを確認する。
3. Aを閉じ、古い状態のBで「今すぐ保存」を押して閉じる。
4. タブCで再開すると100金貨・イリス未雇用に戻る。

UI担当が実Chromiumで再現。手動保存だけでなく、同じ経路の自動保存・非表示時保存にも影響する。再現スクリプトはこのタスクの `/tmp/review_ui_multitab.cjs`（一時ファイル。新規環境での存在は前提にしない）。

推奨: 保存協調処理を切り出し、Web Locks等で書き込み担当を1タブに限定する。他タブには読み取り専用表示や明示的な引き継ぎを提供する。自動保存・手動保存・初期化・離脱保存の全経路に同じ所有権確認を適用する。`storage`イベントやrevisionの比較だけを、完全な排他の代わりにしない。

## P2: 数値変更と途中セーブの互換性

根拠: [合成時間の照合](../src/persistence/save.ts#L58)、[派遣時間の照合](../src/persistence/save.ts#L85)、[報酬の照合](../src/persistence/save.ts#L89)。保存した開始時条件を現在のコンテンツ値と照合している。

ロジック担当は、正規の初期状態から傷薬の合成を開始し、1tick進めたセーブを生成。その後、実行中のモジュール内だけで `recipes.potion.ticks` を80から81へ変更すると、同じセーブが `Save has inconsistent game data` で拒否された。ソースファイルは変更していない。再現スクリプトは `/tmp/alcemy-review-engine.mjs`。

現状では破損扱いとなり、UIの復旧経路が確認付き新規開始に限られる。バランス変更や隣接効果を導入する前に、保存形式のversionとコンテンツのversion、開始済みジョブのスナップショット、移行処理の方針を決める。

推奨: 既知のv1セーブを固定JSON fixtureとして残し、`decode → migrate → validate` の境界を設ける。旧版の時間・報酬を持つ進行中ジョブの扱いを定義する。不正なセーブの検査を一律に緩めて解決しない。

## P2: UIの段階的な分割

根拠: [App.tsx](../src/ui/App.tsx#L31) は775行で、目標判定・選択・配置・派遣先・初期化と、工房・在庫・冒険者・研究・記録の全描画を担当する。[時計](../src/ui/useGame.ts#L66) は100msごとに状態を更新するため、全セクションが同じ頻度で再評価される。

測定された性能不具合はない。分割の主な目的は変更箇所と確認範囲を小さくすること。

推奨: `WorkshopPanel`、`EquipmentDetail`、`ExpeditionPanel`、`InventoryPanel`、`ResearchTree`、`QuestProgress` へ段階的に分ける。ゲーム状態の正本は一つのまま維持し、表示専用のデータと操作を渡す。`memo`等の性能対策はプロファイルで必要性を確認してから行う。

`useGame.ts` は111行で、ファイル長だけを理由に一斉分割する必要はない。P1の対応に合わせて保存協調を切り出し、時計の切り出しは必要になった段階で行う。

## P2/P3: ルールの重複と拡張用の固定値

知識の加算は [UI](../src/ui/App.tsx#L392) と [エンジン](../src/game/engine.ts#L320)、森の報酬は [UI](../src/ui/App.tsx#L604) と [エンジン](../src/game/engine.ts#L113) で重複する。現在の数値不一致はない。

推奨: 合成プレビューと派遣プレビューを共通関数にし、実際のジョブ開始にも同じ関数を使う。時間と売価の既存共通関数と同程度の仕組みで十分。

工房寸法・設備数・研究数は [スキーマ](../src/game/types.ts#L45)、[配置検証](../src/game/engine.ts#L128)、UIに分散する。工房拡張前に `GRID_COLUMNS / GRID_ROWS` と容量計算を共通化し、研究件数はID一覧から導く。研究を増やす段階で効果集計をまとめる。これらは現行の数値が誤っているという指摘ではない。

## P2/P3: 追加すべき回帰テスト

現E2Eの[保存確認](../tests/e2e/smoke.spec.ts#L58)は購入操作直後の文字列を再読み込み後に比較する。単体テストは[現行版での往復](../tests/unit/save.test.ts#L13)を確認する。次を優先する。

1. 同一コンテキストの複数ページで進行・初期化が古いタブに上書きされない。
2. 操作せず時間を進めた後、5秒自動保存に進捗が反映される。
3. 離脱時に最新の残時間が保存され、再読込後にその残時間で帰還・合成が完了する。
4. 現行の生成関数を使わない固定v1セーブfixtureを読み込める。
5. 全E2Eに共通の例外監視を適用する。現在は[最初のシナリオ](../tests/e2e/smoke.spec.ts#L16)だけ。
6. [コンテンツ検査](../tests/unit/engine.test.ts#L349)に、材料数量・所要時間の正整数、価格・費用の有限かつ非負という条件を追加する。

1〜4は保存関連の整理前に優先する。5〜6はP3で、コンテンツ拡大時の事故防止として追加する。

## 既知の仕様制限: 全枠が調合釜の場合

初期状態から通常の派遣・製造・販売で調合釜を24台に増やし、蒸留器の研究と購入費を揃えても、全マスの占有により蒸留器を置けない。[配置](../src/game/engine.ts#L137)は占有を拒否し、[コマンド一覧](../src/game/types.ts#L99)に収納・撤去・交換はない。

既にPLANとPROGRESSに記載された仕様制限で、新発見のコード不具合とは区別する。M2で設備の収納または交換を優先する根拠となる。進行中の材料・残時間・再配置時の扱いを決める必要があり、単なる動作維持のリファクタリングには混ぜない。

## 推奨する作業順

1. 複数タブの再現を回帰テスト化し、保存協調を修正する。
2. 固定v1 fixtureと保存ライフサイクルのテストを追加し、数値変更時の互換性を整える。
3. 既存のゲーム動作を維持してAppを分割し、プレビュー計算と固定値を限定的に共通化する。
4. その後に設備収納・隣接効果・研究追加などのM2機能へ進む。

各段階で `npm run check` を通し、機能追加と整理を別のcommitにする。

現段階ではRedux、新しいゲームエンジン、ECS、イベントソーシング、汎用ルールDSL、CSSの全面置換、テストフレームワーク変更は必要ない。依存のexact固定・lockfile・Action SHA固定・成功したビルドのみのデプロイ・公開パス検証は維持する。現CIの所要時間に対して大規模なキャッシュ基盤やジョブ細分化も優先しない。

参考として、安全整数の極端な値を含む保存を編集すると、演算後の値が復元上限を超えるケースも再現された。通常プレイでは事実上到達不能なため、今回の優先修正には含めず、長期的な数値拡張時に扱う。
